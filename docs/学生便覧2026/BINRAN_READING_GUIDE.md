# 学生便覧の読み込みルールブック

神戸大学の学生便覧PDFから必修科目・履修要件（単位チェッカー用の合算制約等）を抽出する際の標準手順。
[[project_required_subjects_feature]]（機械工学科）と[[project_credit_checker_department_expansion]]（経営学部）で確立した手法をまとめたもの。新しい学部・学科に着手する前に必ず目を通すこと。

**重要（2026-07-14〜、恒久ルール）**: 新しい学部・学科の便覧を読むときは、単位チェッカー（credit_requirements・registration_caps）だけでなく、**必修科目自動登録（required_subjects）の洗い出しも毎回セットで行うこと。** ユーザーからの明示指示（文学部対応時）で恒久化した。「単位チェッカーだけ実装して必修科目自動登録は別タスク」という分割は行わない。ただし全ての必修候補が自動登録できるとは限らない（11章参照）。自動登録できない科目が残った場合は、その理由をメモリと管理画面の注記に必ず書き残し、「未対応」で終わらせず次に着手する人が判断できる状態にする。

## 0. 便覧PDFの入手経路（Web公開ページからの特定）

学部によっては学生便覧が学部独自サイトで年度別・章別PDFとして公開されている（例: 農学部 `https://www.ans.kobe-u.ac.jp/zaigakusei/gakubusei/binran.html`）。着手のたびに毎回同じ調べ方をやり直さないよう、手順を固定する。

1. まず該当学部の便覧公開ページをWebFetchで1回読み、最新年度・過去年度の構成（全ページ統合版か章別PDFか）を把握する。
2. **1回目のWebFetch結果は各章のファイル名・URLを省略した要約になりがちなので、必ず2回目に「各章のPDFへのリンク（href属性の実際のURL）を全て抽出して」のように明示的にURL抽出だけを目的とするプロンプトで再度WebFetchする。** 相対パスのまま返ってくるので、ページのベースURLと連結してフルURLにすること。
3. 章立て・ファイル名は数字プレフィックス＋内容名の命名規則が多い（農学部の実例）:
   - `00_{年度}Binran_All.pdf` = 全ページ統合版
   - `02_{年度}gakubukisoku.pdf` / `02_{年度}gakubukisoku_beppyou.pdf` = 学部規則（本体／別表）
   - `03_{年度}gakubunaiki.pdf` = 修学上に関する内規
   - `08_{年度}syugakuannnai.pdf` = 修学案内
   - `09_{年度}GPA_numbering.pdf` = GPA・科目ナンバリング
   - 上記番号・章名は学部が変わると微妙にずれる可能性があるので、確認せず流用しない。
4. **単位チェッカー・CAP制の抽出に必要なのは主に「学部規則（別表含む）」「修学内規」「修学案内」の3章**。全ページ統合版（10MB超）を毎回ダウンロードする必要はなく、この3章だけ個別取得すれば足りることが多い。
5. WebFetchはHTML→テキスト変換までしか行わないため、PDF本体の表構造をpdfplumberで解析する場合は改めてBash等で実ファイルをダウンロードし、既存の`docs/学生便覧{年度}/`命名規則（1章参照）で保存すること。

## 1. ファイルの置き場所・命名規則

- 便覧関連ファイルは全て `docs/学生便覧{年度}/`（例: `docs/学生便覧2026/`）にまとめて保存する。
- 便覧PDF本体: `docs/学生便覧{年度}/binran_{年度}_{学部略称}.pdf`（例: `binran_2026_koubu.pdf`＝工学部, `binran_2026_keiei.pdf`＝経営学部）
- 抽出したテキスト: `docs/学生便覧{年度}/binran_{年度}_{学部略称}_{学科略称}.txt`（学科別に該当ページだけ抜き出したもの。例: `binran_2026_koubu_kikai.txt`＝工学部機械工学科）
- 表構造確認用の中間ファイル（`table_p{ページ番号}.txt`／`page_{ページ番号}.png`等）も同じ `docs/学生便覧{年度}/` フォルダに保存する。
- `docs/` はディレクトリ全体が `.gitignore` 対象（個人名入り成績表PDF等が混在するため）。このルールブック自体もリポジトリには含まれない。他セッション・他端末で参照させたい場合は `git add -f` するか、要点をメモリ（[[project_required_subjects_feature]]等）にも書き残すこと。

## 2. PDF抽出の手順

1. まず `pdfplumber` の `page.extract_text()` で全ページテキスト抽出を試みる。
2. **神戸大学の便覧PDFはフォントのToUnicodeマップが壊れている個体があり、pdfplumber/PyMuPDFのテキスト抽出がそのまま文字化けすることがある。** その場合は `fitz`（PyMuPDF）で `page.get_pixmap(matrix=fitz.Matrix(2,2))` 等の高解像度で画像化し、Readツールで画像として直接読む方式に切り替える。
3. 表構造（学科別履修科目一覧表など）は `page.extract_tables()` でも試すが、**rowspan/colspanが絡む入れ子構造（例:「8単位」の対象範囲と「12単位」の対象範囲が別セルにまたがる）は誤読しやすい。** 数値の範囲・対象科目群が絡む箇所は、抽出結果を鵜呑みにせず `page.to_image(resolution=200)` でPNG化し、Readツールで目視確認するのが最も確実。
4. Windowsコンソールへの直接出力は日本語が化けることがある。抽出スクリプトは `print()` に頼らず、`PYTHONIOENCODING=utf-8` を設定した上でUTF-8ファイルに書き出し、結果はReadツールでファイルから読むこと。

## 3. 表の読み方（別表の凡例）

学部規則の「別表」（学科別開設科目一覧）は以下の凡例が一般的（学部により表記が微妙に違うので必ず該当ページの凡例注記を確認すること）:

- `◎` = 必修科目
- `○`/`△` = 選択必修科目（グループ内から一定数選択）
- 無印 = 選択科目

「必修・選択の別」列と「授業科目の区分」列（共通専門基礎科目／専門基礎科目／専門科目 等の大区分）は別軸なので混同しないこと。

## 4. 既存DB・コードとの突き合わせ方針（ブラインドテスト推奨）

ユーザーは「既存のDB/コードを見ずに便覧だけからデータを作り、あとで既存実装と突き合わせる」方式を好む（[[project_credit_checker_department_expansion]]参照）。これは既存実装のバグ発見に有効だった実績がある。

- **作業開始前に、対象学部のフロントコード（`timetable.html`等）や既存DB値を不用意に読まないこと。** 一度読むとマジックナンバー等の予備知識が残り、後で「本当に見ずにやったか」と問われた際に真に独立した検証と言えなくなる。
- ブラインド抽出が必要かどうか判断に迷う場合は、着手前にユーザーに確認する。
- 抽出後にDBの値を語る際は、必ず実クエリで確認する。`database.py`のシードINSERT文だけを見て「これがDBの現在値」と早合点しない（管理画面編集や別セッションで既に変わっている場合がある）。

## 5. よくあるデータ品質の罠

便覧の科目名・構造とDB（`subjects`/`syllabi`）は機械的な完全一致ができないことが多い。突き合わせ時は以下を疑うこと。

- **ローマ数字表記ゆれ**: 半角(`I`/`II`)と全角(`Ⅰ`/`Ⅱ`)が科目ごとに不統一。`normalize_subject_name`で吸収されるが、便覧側の手入力データではそのまま残ることがある。
- **クォーター分割**: 便覧では1科目でも、DB側はクォーター別に別レコード（`syllabi`）に分かれていることがある（例:「機械製図Ⅰ」が「機械製図I(1Q)」「機械製図I(3Q)」の2レコード）。
- **科目の欠落**: 便覧に載っているのにDBに存在しない科目がある（シラバス側で前期科目のcourse_section未作成等が原因、[[project_credits_instructor_backfill_20260710]]参照）。時間割コードを2025年度時間割PDF等で特定し、`import_syllabus.py`で補完する。
- **入れ子の合算制約**: 便覧の履修要件表に「A区分＋B区分＝8単位以上」「A+B+C+D区分（全体）＝12単位以上」のような多重の合算行が存在することがある（経営学部の教養科目8単位/12単位、専門科目55単位/98単位が実例）。DB設計は`credit_requirements.combined_of`(JSONB)/`max_credits`で表現する仕組みが既にあるので、新学部で同様の構造が見つかってもフロント・バックエンドの追加実装は不要、DBデータ追加だけで対応できる。
- **「98単位」等のマジックナンバーの対象範囲を誤認識しやすい**: 「関連科目」「その他必要と認める科目」等の注記付き科目群を合算対象に含めるかどうかは便覧本文を熟読しないと誤る（経営学部で過去に誤りが発覚した実例）。

## 6. 特殊な履修分岐に注意

便覧の◎（必修）表記だけでは判定しきれない分岐が学科ごとに存在しうる。時間割表の脚注・注意事項も必ず確認すること。

- 例（機械工学科）: 「機械製図Ⅰ・Ⅱ」と「機械工学実習Ⅰ・Ⅱ」は便覧上両方◎だが、実際は学籍番号の偶奇で二者択一（偶数→実習、奇数→製図）。`user_profiles.student_id`（数字7桁+学部コード）の末尾1桁で判定可能。
- 自動登録機能を実装する場合、こうした分岐ロジックを見落とすと過剰登録になるので、対象学科に着手する際は脚注を必ず探すこと。

## 7. 履修登録単位数の上限（CAP制）の算出方法

`registration_caps`テーブル（[[project_registration_cap_feature]]）に投入するCAP値（年間の履修登録単位数の上限）は、便覧の以下の位置にほぼ確実に載っている。

1. **検索キーワード**: `CAP制`／`履修.{0,4}登録.{0,10}上限`／`登録できる単位数`／`登録単位数の上限` でPDF全文を検索する。全学共通の説明（「履修登録前までに…」「用語の解説」等のページ）にも出るが、これは制度の一般説明にすぎず具体的な単位数は載っていないので読み飛ばしてよい。
2. **本命は「◯◯学部規則」内の「履修科目の登録の上限」という見出しの条文**（工学部は第6条、経営学部は第8条など、学部により条番号は異なる）。文面は概ね「教学規則第29条第1項の規定に基づく履修科目の登録の上限は，◯◯単位とする。」という定型パターンで、ここに具体的な単位数が明記されている。
3. 学部規則本体とは別に「履修科目の登録の上限に関する細則」という独立した細則が存在することがある（経営学部の実例）。ここには**学期ごとの上限枠の有無**（例:「各学期毎の履修科目の登録の上限の枠は設けない」＝年間トータルのみで判定）や、成績優秀者・交換留学プログラム参加者向けの緩和規定が載っているので、CAPの適用単位（学期単位か年間単位か）を誤解しないために必ず確認する。
4. 学部により**学科をまたいで一律の値**（工学部は5学科すべて54単位で共通）と、**学科ごとに値が異なる**ケースの両方があり得る。学部規則の条文だけでなく、学科別の「履修上の注意」ページ（別表の脚注など）で学科ごとに再掲されていないか確認し、値が食い違っていないか突き合わせる。
5. **CAPに算入されない科目**の除外規定に注意する（例: 経営学部の「卒業論文」、「グローバルチャレンジ実習」等をCAP対象外とする申合せ）。これらは`registration_caps`のシンプルな年間合計値には影響しないが、将来UI側で「登録済み単位数」を計算する際に対象外科目を除外する必要が出てくる可能性がある。
6. **CAPを超えて登録できる例外者の基準**（早期履修認定・成績優秀者・交換留学プログラム等）も便覧に定めがあるが、現行の`_get_registration_cap()`（`routers/timetable_api.py`）は学部・学科・年度の一律値のみを見る設計で、個人単位の緩和は反映されていない。値を投入する際はこの割り切りを踏まえ、例外規定はメモリに書き残すだけで実装対応は不要（超過時も警告のみで登録はブロックしない仕様のため実害が小さい）。
7. `registration_caps.year`は**入学年度ではなく、その履修登録が行われる授業開講年度（西暦）**と突合される（`syl.year`と一致させる設計）。便覧が「令和◯年度入学者用」と書かれていても、記載されているCAP値は基本的にその年度に在学する全学年に適用される値として登録してよい。

## 8. 学部・学科の正式名称

正式名称の表記ゆれ（旧学部名・学科名の誤り等）は[[project_faculty_department_master]]を参照。便覧の学部規則名（「○○学部規則」）とDBの`faculty`列の値が一致するとは限らないので、`FACULTY_PATH`（`core/config.py`等4箇所）の対応表と突き合わせること。

## 9. 単位チェッカー（credit_requirements）DB設計の一般化ルール

新しい学部・学科の単位チェッカーを追加する前に、既存実装の以下の制約を必ず確認すること。DBの値はWindowsコンソールに直接printすると文字化けするので、必ずUTF-8ファイルに書き出してReadツールで確認する（0章と同じ理由）。

1. **`credit_requirements.category_id`は学部をまたいだグローバルな主キー**（faculty列はWHERE絞り込み用でしかなく、複合主キーではない）。`jinbun`/`shakai`/`shizen`/`sougou`/`kyoyo_kiban`/`gaigo1`/`gaigo2`/`kyotsu`という**裸の名前は経営学部が先に使用済み**のため、他学部で同種のカテゴリを追加する場合は必ず学科キーで前置する（例: 工学部市民工学科の`shimin_jinbun`）。着手前に`SELECT category_id FROM credit_requirements`で既存IDと命名規則を確認すること。
2. **取得単位の自動反映（`templates/liff/timetable.html`の`applyEarnedCredits()`）は、category_idの文字列が成績表解析結果（`classify_seiseki_raw()`が返すdict、キーは`jinbun`/`shizen`/`shakai`/`sougou`/`kyoyo_kiban`/`gaigo1`/`gaigo2`/`kyotsu`/`senmon_all`等）と完全一致する場合のみ機能する。** 前置プレフィックス付きのcategory_id（`shimin_jinbun`等）はこの完全一致に当たらないため、**現状「専門科目（選択科目含む）」区分（idが`_senmon`で終わる場合のみ`senmon_all`から補完）以外は自動反映されない**（工学部の人文系/社会系/自然系/総合系/外国語区分は取得欄が常に0のまま、という既知の未修正ギャップ。新学部追加時にこの穴を埋めるかどうかは着手前にユーザーに確認する）。
3. **`共通専門基礎科目`と`専門科目`を別々の必要単位数として持つ学部**（経営学部の群無し学部で、かつ両者の必要単位数が異なる場合）は、`classify_seiseki_raw()`が返す`kyotsu`（共通専門基礎科目のみ）と、**専門科目のみの値（`senmon_all`から`kyotsu`を差し引いた値。現状は個別キーとして返していないため、新設が必要になることがある）**を区別して使うこと。一方、**両者をまとめて1つの必要単位数として扱う学部**（機械工学科等、便覧の別表が「共通専門基礎科目＋専門科目」を分けずに1本で必要単位数を定めている場合）は、既存の`senmon_all`（`kyotsu`＋専門科目の合算値）とid末尾`_senmon`の仕組みがそのまま使える。便覧の別表第2で必要単位数が「共通専門基礎科目」列と「専門科目」列で別々の数字になっているか、1本にまとまっているかを必ず確認してから設計を決めること。
4. **入れ子の合算制約**（人文系＋社会系＝8単位、さらに自然系＋総合系を加えて10〜12単位、等）は、まず各カテゴリの葉（jinbun/shakai/shizen/sougou相当）を`required_credits=0`の行として個別に作成し、その上で`combined_of`にそれらのcategory_idリストを入れた合算行を追加する（`sort_order`は葉より後ろにする）。葉のカテゴリ行が存在しないと合算行の取得単位が常に0になる。
5. **学科の下にさらに「コース」等の細分がある学部**（2年次以降に分岐する等）で、コースごとに必要単位数が違う場合は、`UserProfile.department`／`CreditRequirement.department`の値そのものをコース名にする（工学部の学科と同じ扱い＝学生が実際に進級後に選ぶ最小単位を`department`として登録する）。1年次でまだコース未定の学生がいる場合、`department`をNULL許容のままにし、フロント側でコース未選択時は学科共通部分（`department`がNULLの行）のみ表示するなどのUXを検討する（要ユーザー確認）。
6. **便覧の別表で特定コースだけ「別に定める指定科目から修得すること」等の例外注記がある場合**（＝この便覧内の数字だけでは必修/選択の内訳を機械的に確定できない場合）、無理に内訳を推測せず、合計値のみ`required_credits`に設定し、内訳の注記は`note`列に転記した上でユーザーに一言確認する。

## 10. 必修科目自動登録（required_subjects）が「できないケース」の見分け方

別表2で「必要修得単位数」が名指しの単一科目とちょうど一致していても、以下のいずれかに該当する場合は`required_subjects`へ機械的に登録してはいけない（文学部対応（2026-07-14）で類型化）。該当する場合は`credit_requirements.note`にその旨を明記し、対象外のまま次の担当者に引き継ぐ。

1. **並行クラスが多数あり、学生がどのクラスに割り当てられるか判定する情報がDBに無い**（例: 文学部のAcademic English系科目は1科目につき28〜30人の教員が並行して同一科目を担当しており、学生ごとにどのクラスへ配属されるかはDBの`course_sections`/`syllabi`だけでは分からない）。`Subject`に対して`CourseSection`が異常に多い（10件超）場合はまずこのパターンを疑う。
2. **学生本人の選択に依存する**（例: 外国語第Ⅱのドイツ語/フランス語/中国語/ロシア語からの選択、便覧内の複数科目からの選択科目群）。`UserProfile`に選択結果を保持するカラムが無い限り確定不可能。
3. **指導教員ごとに別科目として登録されている**（例: 文学部の「卒業論文」は指導教員43名分がそれぞれ別の`Subject`行として存在する。農学部の「卒業研究」も同様のパターンが過去に見つかっている）。学生の配属研究室が分からないと確定できない。
4. **DBに該当科目そのものが存在しない**（例: 文学部の「初年次セミナー」は便覧には単一科目として明記されているが、`data/syllabus_*.txt`の元データに含まれておらずDB未登録だった）。時間割コードを別途調査してimport_syllabus.pyで補完しない限り登録できない。
5. **学年(grade)が単一に確定できない**（2026-07-16、農学部5コース・工学部4学科対応で新規発見）。`required_subjects.grade`は`core/required_subjects.py`の`auto_register_required_subjects()`で学生の現在学年と完全一致でしか自動登録が発動しない設計。一方、`Syllabus.target_grades`（開講対象学年）は「1,2,3,4」のような広い範囲がほとんどで、便覧の別表第1（◎/○表）にも学年情報は無い。別表第1・`Syllabus`だけでは判断できず、学部が別途定める「年次配当表」相当の資料が無いと単一学年へ絞り込めない。誤った学年でINSERTすると別学年の学生に誤登録されるため、この場合も登録を見送ること。

これらに該当しない、かつ便覧の必要修得単位数が単一の名指し科目とちょうど一致する科目（文学部の基盤系4科目＝教養とは何か・多言語と多文化の世界・情報基礎・データサイエンス基礎学が実例）だけを`required_subjects`へ登録する。DB照合時は`Subject`の該当科目に紐づく`CourseSection`→`Syllabus`（`year=DEFAULT_ACADEMIC_YEAR`）が一意に定まるか、かつ`grade`が単一に確定できるか必ず確認すること。

## 11. トークン消費を抑える鉄則（2026-07-14〜、恒久ルール）

200ページ規模の便覧PDFを毎回LLMのコンテキストに読ませるとトークン消費が激しいため、**「LLMに見せる前にどれだけ機械的に絞り込めるか」を必ず先に検討すること。** サブエージェントに丸投げしても合計トークン消費は減らない（サブエージェント自身がその分を消費するだけ）ので、根本対策にはならない。

1. **抽出済みファイルの再利用を最優先する**: 対象学部・章のtxtが`docs/学生便覧{年度}/`に既にあれば、絶対にPDFを再度開かない。作業開始前に必ずこのフォルダの既存ファイルを確認する。
2. **章単位よりさらにページ単位で絞る**: 0章4項で「学部規則」「修学内規」「修学案内」の3章だけに絞る運用は既にあるが、それでも数十ページに及ぶことがある。可能な場合はBash/PowerShellの`grep`/`Select-String`等（LLMを介さない機械的な文字列検索）で「履修科目の登録の上限」「◎」等のキーワードを含むページ番号を先に特定し、**該当ページ番号だけ**をpdfplumber/fitzでテキスト化・画像化してからReadツールで読む。ページ番号を絞らずに章全体をそのままReadに渡さない。
3. **PNG目視確認は疑わしいページだけに限定する**: 表構造が怪しい（rowspan/colspan絡みの数値範囲がある等）特定ページのみ画像化する。念のため全ページを画像化するような保険はかけない。
4. これらの絞り込みは全て「PDFファイルに対する機械的な前処理スクリプト」の段階で完結させ、その結果（絞り込み後のテキストやページ番号リスト）だけをLLMとのやり取りに持ち込むのが唯一の効くレバーである。
